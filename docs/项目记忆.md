## 一、项目是什么

**ESP32-S3 桌面宠物**：一块 2.0 寸 SPI 屏循环播放角色动画，外壳做成摆件。

- 硬件：ESP32-S3-WROOM-1 **N16R8**（16MB Flash + 8MB Octal PSRAM）+ 2.0 寸 ST7789（320×240 横屏）
- 角色名：西米（原创，素材为 640×360 WebP/WebM alpha 视频）
- 素材规模：**106 段**动画，总时长约 1060 秒

**核心链路**：

```
WebM(alpha) ──pipeline.py──▶ .petpack(JPEG 序列) ──▶ LittleFS/SD
                                                        │
                          core1: 读帧 → JPEGDEC 解码 → PSRAM 后缓冲
                                                        │ 双缓冲交换
                          core0: DMA pushImage @40MHz → ST7789
```

## 五、关键决策与理由（别轻易推翻）

### 1. 用 JPEG 序列，不用 H.264

ESP32-S3 **没有硬件视频解码**。软解 H.264 的 320×240 需要十几 ms 以上且占用大量 RAM；JPEGDEC 有 S3 SIMD 汇编优化，320×240 单帧约 29ms，可预测、可丢帧。

### 2. 素材与屏幕 1:1，放大在流水线完成（最重要）

**踩坑历史**：早期素材是 320×180，固件运行时放大到 320×240，试了 1.33 / 1.40 / 1.50 / 1.60 / 2.0 五档。

| 倍数 | 配置 | 实测 |
|:---|:---|:---|
| 1.33 | 4/3 | 人物明显偏小 |
| 1.50 | 3/2 | 人物完整、大小合适 |
| 2.00 | 2/1 | 切掉头发和脚 |

**结论**：运行时放大只是把已有像素复制/插值，**越拉越糊，且每帧多花 15ms**。原素材 320×180 里人物只有约 105px 高，拉到 240 等于 2.3 倍上采样，物理上不可能清晰。

**现在的做法**：pipeline 从源画面 640×360 **居中裁 426×320**，再 lanczos 缩放到 320×240。全程用源视频真实像素，效果等同于"1.5 倍"但细节是实的。

```python
# tools/pipeline/pipeline.py
WIDTH, HEIGHT = 320, 240
CROP_W, CROP_H = 426, 320   # 改这里要同步改 config.h 的 kFrameW/kFrameH
```

### 3. 双缓冲 + 双核，把 sum 变 max

解码 29ms + 刷屏 30ms 串行 = 59ms，超过 12fps 的 83ms 预算时余量太小。
双缓冲让两者重叠，实测总耗时约 74ms，稳定 13fps。

### 4. 解码必须输出大端（RGB565_BIG_ENDIAN）

`pushImage` 是 **DMA 直发内存字节**，不做任何转换；ST7789 的 SPI 按大端收。
用小端的后果：**红显示成蓝、绿显示成红、蓝显示成绿**（通道循环错位），看起来又糊又花，极易误判为"素材质量差"。

### 5. PSRAM cache 必须手动写回

ESP32 Arduino Core 2.x（IDF 4.4）**没有 `esp_cache.h`**，LovyanGFX 的 `dma_cache_sync` 是空实现。DMA 读到的是脏数据，表现为**横纹 / 噪点**。

解决：用 ROM 的 `Cache_WriteBack_Addr()` 手动写回，代码里包在 `#if defined(PET_HAVE_ROM_CACHE)` 里。

### 6. 分区表去掉 OTA slot

默认 16MB 分区给 spiffs 只有约 3.4MB，装不下素材。去掉 app1 后 storage 拿到 **11.93MB**。

```
app0,     app,  ota_0, 0x10000,  0x400000,   # 4MB
storage,  data, spiffs,0x410000, 0xBF0000,   # 11.93MB
```

### 7. 用 LittleFS 不用 SPIFFS

SPIFFS 是扁平结构、不支持真目录，而素材按分类分目录存放（`/packs/待机/xxx.petpack`）。

### 8. 存储后端抽象

`config.h` 的 `Backend` 枚举 + `platformio.ini` 的 `-DSTORAGE_BACKEND=0|1`，上层代码零改动即可切换 Flash / SD。

## 六、踩过的坑（现象 → 根因 → 解决）

| # | 现象 | 根因 | 解决 |
|--:|:---|:---|:---|
| 1 | 屏全黑，但串口正常 | 背光用了 LovyanGFX `Light_PWM`，实测输出不了电平；且 GPIO13 是 SPI2 默认 MISO | 背光改裸 GPIO `pinMode + digitalWrite(HIGH)` |
| 2 | 黑白颠倒 | `cfg.invert = true` | 改 `false` |
| 3 | 红蓝互换 | `cfg.rgb_order = true` | 改 `false` |
| 4 | 颜色循环错位（红→蓝→绿） | 解码输出小端，DMA 直发被大端 SPI 读走 | `RGB565_BIG_ENDIAN` |
| 5 | 画面横纹 / 噪点 | PSRAM cache 未写回，DMA 读脏数据 | `Cache_WriteBack_Addr()` |
| 6 | 80MHz 黑屏 / 花屏 | 杜邦线撑不住 80MHz | 40MHz（20MHz 为保底） |
| 7 | PSRAM 分配失败 | `memory_type = qio_qspi` 与 Octal PSRAM 不符 | 改 `qio_opi` |
| 8 | 画面模糊，放大越多越糊 | 运行时插值造不出细节 | 放大搬到 pipeline（见决策 2） |
| 9 | pipeline 输出只剩左上角一块 | filter 顺序错（先 overlay 后 scale） | 顺序必须是 **crop → scale → overlay** |
| 10 | 局部转换把 106 段索引覆盖了 | 冒烟模式也写全量 `index.json` | `--limit/--only` 时改存 `docs/smoke_index.json` |
| 11 | `LittleFS.begin` 挂错分区 | 4 个参数里第 4 个是 **partitionLabel** 不是挂载点 | 用 `kFlashPartLabel = "storage"` |
| 12 | 文件永远打不开 | FS 层会自动拼 mountpoint，代码又拼了一次 | 代码里只写 `/packs`，不写 `/storage/packs` |
| 13 | 播放直接失败 | `.petpack` 头的 w/h 与 `kFrameW/H` 不匹配 | 转素材时尺寸必须同步 `config.h` |
| 14 | 鼠标拖大的素材放不进 Flash | 320×240 比 320×180 体积 **+79%**（716KB → 1284KB/段） | Flash 只放 8 段（10.48MB），全量必须 SD 卡 |
| 15 | 想让某段循环、又想自动换段 | 素材包 `loop` 标志恒为 1 | `player::play(path, once=true)` 忽略包内标志 |
| 16 | 复制素材误把 106 段全塞进 Flash | PowerShell 脚本用 `-Recurse` 扫了 source 目录全部 | 按精确路径逐个 `Copy-Item` |

## 八、常用命令

```powershell
# 烧固件
.\tools\flash.ps1 -Target fw -Port COM16

# 烧素材（Flash 分区）
.\tools\flash.ps1 -Target fs -Port COM16

# 两个都烧
.\tools\flash.ps1 -Target all -Port COM16

# 只转某一段素材（名字包含子串即可）

# 全量转 106 段（约 3.2 分钟）

# 只处理前 3 段（冒烟）
& 'C:\Users\PC207\.platformio\penv\Scripts\python.exe' tools\pipeline\pipeline.py --limit 3
```

**Python 路径固定**：`C:\Users\PC207\.platformio\penv\Scripts\python.exe`（不是系统 Python）
**串口**：COM16（按实际改），115200

**Windows 编码注意**：PowerShell 里跑 Python 前必须设 `$env:PYTHONIOENCODING='utf-8'` 和 `$env:PYTHONUTF8='1'`，否则中文素材名会乱码。用 here-string 传给 `python -` 会带 BOM，改用临时文件。

```powershell
# 发布一个正式版（交互录入变更 → 构建 → 合并 → 归档到 releases/vX.Y.Z/ → 打 tag）
& 'C:\Users\PC207\.platformio\penv\Scripts\python.exe' tools\release.py v1.1.0 --tag
```

### 版本发布管理（tools/release.py）

- **目录**：`releases/vX.Y.Z/`，内含 CHANGELOG.md（功能变更 + ⚠硬件变更特别备注）、烧写说明.md、
  `dshpet-vX.Y.Z-merged.bin`（约 540KB，地址 0 一键烧）、`dshpet-vX.Y.Z-littlefs.bin`（约 12MB，烧 0x410000）、MD5SUMS.txt
- **版本规则**：主版本=大功能/硬件变更，次版本=新功能，修订号=bug 修复
- **流程**：脚本先写 `firmware/src/version.h`（版本号编进固件，开机日志 `[pet] boot vX.Y.Z` 自报）
  → pio 编译 → esptool merge_bin（不填满 16MB，只到 app 段结束）→ 生成文档 → 更新 `releases/README.md` 索引 → git tag
- **bin 全部入库 git**：`*.bin` 全局忽略但 `!releases/**/*.bin` 负向放行，用户确认接受仓库增长
- 版本号重复 / releases 目录已存在 / git tag 已存在都会被脚本拒绝，防覆盖

## 十、给下一个 AI 的注意事项

1. **`config.h` 是唯一常量来源**，改引脚/尺寸/频率只动这里，但 **`pipeline.py` 的 `WIDTH/HEIGHT/CROP_*` 必须同步**，否则 `.petpack` 校验会拒绝加载。
2. **改显示相关代码后把 `kFwVersion` +1**，开机屏会显示，这是最快的版本确认手段。
3. **不要重新引入运行时缩放**。如果觉得人物小，改 `pipeline.py` 的 `CROP_W/CROP_H` 重转素材，不要改固件。
4. **别用 `git add .`**。素材 `*.petpack`、`*.webm`、`tools/ffmpeg/`、`firmware/.pio/` 已被 gitignore，但 `firmware/data/packs/` 下误放的包会撑爆仓库。
5. **测试前先看串口**：`[pet] 扫到 N 段`、`[player] 播放 …`、`[animator] 切换 → …` 能直接定位问题层次。
6. **当前播放行为**：8 段洗牌轮播，每段播完自动切下一段，一轮内不重复。想改成别的调度，改 `animator.cpp`。
7. **`docs/阶段1-硬件接线教程.md` 里标注 ⚠️ 的内容都还没上机**，不要当成已验证事实引用。
