# 把 dsh-pet 动画搬到 ESP32 屏幕上：技术方案

> **结论先行**：转 **MJPEG（每帧独立 JPEG）+ 自定义容器 `.petpack`**，下采样到 **320×180**，帧率降到 **12～15fps**，**把 alpha 提前烘焙进背景**，素材放 **SD 卡**，主控用 **ESP32-S3 + 8MB PSRAM**。
> 这条路的每一个环节都有成熟的开源实现（LovyanGFX + JPEGDEC + SD），不需要自己写解码器，两周内能出能跑的样机。

---

## 一、为什么是 MJPEG（格式选型）

先看素材：640×360 / 24fps / VP9-alpha / 单段 5～10 秒 / 全部 106 段共 51.8MB。

ESP32 侧的现实约束：

| 约束 | 数值 | 影响 |
|:---|:---|:---|
| 主频 | 240MHz 双核（S3） | 软解 H.264 **不可能**，软解 JPEG 可行 |
| PSRAM | 8MB（S3 N16R8） | 单帧 RGB565 缓冲 150KB，够双缓冲 |
| Flash | 16MB | 只够放几段素材，装不下 51MB |
| SPI 屏带宽 | 80MHz ≈ 8～10MB/s | 320×240@24fps 需 3.7MB/s，够用 |
| 硬件解码器 | **无**（S3 没有 JPEG/H.264 硬解） | 全靠软解，选解码成本低的格式 |

候选格式对比：

| 格式 | 解码成本 | 压缩率 | 透明支持 | 结论 |
|:---|:---|:---|:---|:---|
| **MJPEG** | 中（JPEGDEC 单帧 15～25ms） | 中（约 8～15KB/帧 @320×180） | 无（需预合成） | ✅ **推荐**：库成熟、可跳帧、可从任意帧起播 |
| GIF | 高（LZW 慢） | 低 | 1-bit | ❌ 又慢又大 |
| PNG / APNG | 极高 | 高 | ✅ | ❌ 解码太慢 |
| H.264 / VP9 | 无硬解 | 最高 | — | ❌ 放不了 |
| RGB565 裸帧 | 无（DMA 直出） | 无（150KB/帧） | 需自己处理 | ⚠️ 只在 SD 直读整段短片时用，体积爆炸 |
| RGB565 + RLE | 极低（1～2ms） | 中（约 20～40KB/帧） | 需自写掩码 | ⚠️ MJPEG 帧率不够时的**备选** |
| QOI | 低 | 中 | ✅ 可带 α | ⚠️ 折中方案，生态少 |

一句话：**MJPEG 是 ESP32 上唯一"压缩够用 + 解码扛得住 + 生态齐全"的选择**。

## 二、素材转换流水线（PC 上一次性做完）

### 2.1 转换参数

| 参数 | 建议值 | 理由 |
|:---|:---|:---|
| 分辨率 | **320×180**（16:9，正好是 640×360 的一半） | 对应 320×240 屏，上下留 30px 给背景/状态栏 |
| 帧率 | **12～15fps** | 原 24fps 对桌宠是浪费；12fps 肉眼可接受，数据量直接砍半 |
| JPEG 质量 | **q=75**（先用 q=80 试，超预算就降） | 卡通画面 q75 基本无损 |
| 色彩 | RGB（yuvj420p） | 屏是 RGB565，无需再优化色度 |
| 背景 | **预合成**（把透明区压到一张固定背景上） | 省掉逐帧 alpha 运算；屏是专用装饰屏，不需要真透明 |
| 帧数 | 每段截前 **3～5 秒**或用整段 | 待机类可全保留，玩耍类截短可省 60% 空间 |

> 想做"屏后面是真的桌面/环境"这种效果，就不要预合成，改用**色键**：导出时垫纯品红底（#FF00FF），固件里解码后逐像素把品红置换成背景——代价是边缘有锯齿、每帧多一次全屏遍历（320×180 约 57k 像素，S3 约 2～3ms，可以接受）。

### 2.2 转换命令

```bash
# 1) 单段素材 -> 320x180 / 12fps / q75 的 JPEG 帧序列
ffmpeg -i "待机呼吸休闲.webm" \
       -vf "scale=320:180:flags=lanczos,fps=12" \
       -q:v 3 -pix_fmt yuvj420p "frames/待机呼吸休闲_%04d.jpg"

# 2) （可选）预合成背景：先把素材压到背景图上层
#    background.png 与 320x180 同尺寸
ffmpeg -i "待机呼吸休闲.webm" -i background.png \
       -filter_complex "[0:v]scale=320:180:flags=lanczos,fps=12[fg];[1:v][fg]overlay=0:0:format=auto,format=yuvj420p" \
       -q:v 3 "frames/待机呼吸休闲_%04d.jpg"
```

> ⚠️ **本机当前的 ffmpeg 是精简编译版**（只编进了 x264 编码 + mp4 封装），既不能输出 JPEG 序列也不能读 webm 的透明通道。先装一个完整版：
> `winget install Gyan.FFmpeg` 或 `choco install ffmpeg`，装完 `ffmpeg -version` 能看到 `libx264/libvpx/vp9` 全量列表即可。

### 2.3 打包成 `.petpack`（自定义容器）

把一堆 JPEG 拼成一个文件，好处是**每帧有固定偏移、能随机起播、能跳帧**，不用在 SD 上边读边找 JPEG 结束标记。

```
偏移  长度  内容
0     4     magic  "PETP"
4     2     version = 1
6     2     width         (320)
8     2     height        (180)
10    2     fps           (12)
12    2     frameCount
14    4     flags         (bit0 = 循环)
18    4     reserved
22    4*N   frameOffset[] 相对文件头起（N = frameCount）
22+4N ...   JPEG 数据区（逐帧首尾相接）
```

一帧 = 一段完整 JPEG。播放时：读偏移 → 从 SD 读该帧 → 解码 → 刷屏。

**体积估算**（320×180 / q75 / 卡通画面，**估算值，需实测校准**）：

| 项目 | 单帧 | 3 秒 @12fps | 106 段总量 |
|:---|:---|:---|:---|
| 320×180 | 8～14 KB | 36 帧 ≈ 0.3～0.5 MB | 约 120～180 MB |
| 240×135 | 5～8 KB | 36 帧 ≈ 0.2～0.3 MB | 约 70～110 MB |
| 160×90 | 2.5～4 KB | 36 帧 ≈ 0.1～0.15 MB | 约 35～60 MB |

结论：**106 段全放 Flash 不可能（16MB），必须走 SD 卡**。Flash 里只留 3～5 段最常用的（待机 / 拖拽 / 点击），保证上电秒开、不插卡也能动。

## 三、硬件选型

| 部件 | 推荐型号 | 参考价 | 说明 |
|:---|:---|:---|:---|
| 主控 | **ESP32-S3-WROOM-1-N16R8**（16MB Flash + 8MB PSRAM） | ¥35～50 | 必须有 PSRAM；S3 有 LCD_CAM/DMA，SPI 屏刷新快 |
| 屏幕 | **2.0"～2.8" IPS，320×240，ST7789 / ILI9341**（SPI） | ¥30～60 | 320×180 内容 + 上下留白正好；圆屏 GC9A01 240×240 也可以但会裁切 |
| 存储 | **MicroSD 卡座（SPI）+ 8GB 卡** | ¥10 + ¥25 | 106 段全放进去还有富余；读速 2～3MB/s 远高于需求 |
| 交互 | 电容触摸（TTP223）或板载 BOOT 键 | ¥2 | 点击切动作；不做也行，纯自动轮播 |
| 供电 | USB-C 5V / 锂电池 + TP4056 | ¥10 | 桌面用直接 USB 供电 |

> **不建议** ESP32-C3（无 PSRAM，单帧都放不下）、ESP32-CAM（性能弱、SPI 引脚被摄像头占用）、ESP32-P4（性能过剩，且 MIPI 屏成本和资料门槛都上一个台阶）。

## 四、固件设计

### 4.1 数据流

```
SD 卡 ──SPI(20MHz)──> [读 1 帧 JPEG ~12KB] ──> JPEGDEC 解码 ──> RGB565 缓冲(PSRAM)
                                                                     │
                                                     DMA ────────────┘
                                                       ↓
                                              ST7789 (SPI 80MHz)
```

### 4.2 模块划分

| 模块 | 职责 | 关键点 |
|:---|:---|:---|
| `storage` | 挂 SD、扫 `.petpack`、读帧 | 用 `sdmmc`/`SD.h`，读帧按偏移 + 长度，**顺序读**才能跑到 2MB/s |
| `decoder` | JPEGDEC 解到 RGB565 缓冲 | 开 `JPEGDEC` 的 `RGB565` 输出、`useFrameBuf`；解码回调里直接写屏幕 |
| `display` | LovyanGFX 驱动屏 + DMA 刷屏 | 开双缓冲，`startWrite/pushImage`，别用逐像素画点 |
| `player` | 按帧率调度、循环、跳帧 | 用 `esp_timer` 定时触发；**解码慢就丢帧**（保持时间轴，不等帧） |
| `animator` | 状态机：待机链 / 点击 / 拖拽 / 定时小动作 | 与插件同一套逻辑的极简版：权重抽签 + 不连续重复 |
| `input` | 触摸/按键 | 防抖 + 长按/短按 |

### 4.3 关键实现细节（踩坑点）

1. **双缓冲**：一个缓冲在解码、一个在 DMA 刷屏，否则必然撕裂。PSRAM 里放 2×（320×180×2B ≈ 113KB）毫无压力。
2. **解码直接写缓冲**（JPEGDEC 回调），不要在中间再拷一次。
3. **丢帧不卡时间轴**：目标 12fps = 83ms/帧。若解码+刷屏用了 120ms，就直接跳到下一帧对应的时间点，而不是排队——否则动画会越播越慢。
4. **SD 顺序读**：容器把一帧一段连续存放，用 `f_lseek` 定位后整段 `f_read`，避免逐块随机读。
5. **首帧秒开**：Flash 分区里放一段 12 帧的"待机缩略版"（约 150KB），上电先播它，SD 挂载成功后再切到高清池。
6. **JPEG 色彩**：屏是 RGB565，解码输出直接 565，别走 888 再转，省一次全屏遍历。

### 4.4 性能预算（~~估算~~ → **2026-10-27 已用实测校准**）

> ⚠️ 原估算偏乐观。校准依据：别人的 **240×240 实测 = 57,600 像素，与我们的 320×180 完全相同**，
> 可直接套用。详见 [调研-同类项目与解码库实测.md](调研-同类项目与解码库实测.md)。

| 环节 | 原估算 | **实测** | 说明 |
|:---|:--:|--:|:---|
| 读一帧（SD 6KB / Flash <1ms） | 6～10ms | 5ms（SD） | Flash 阶段更快，且可内存直解省拷贝 |
| JPEG 解码 320×180（JPEGDEC + SIMD） | 15～25ms | **28.91ms** | 原估偏乐观 |
| SPI 刷 320×180 RGB565（113KB） | 14～18ms | **28.10ms** | 实测 SPI 效率仅约 60%，**必须开 DMA** |
| **串行合计** | 35～53ms | **57.01ms** | 12fps(83ms) 余量 **31%**（原估 40%） |

**★ 关键优化：双核并行后帧时间减半**

上表是 decode 与 draw **串行相加**。S3 是双核，用双缓冲让「核 1 解下一帧」与
「核 0 DMA 刷当前帧」重叠：

```
串行  sum(decode, draw) = 57.01ms   → 12fps 余量 31%
并行  max(decode, draw) ≈ 29ms      → 12fps 余量 64%，理论可冲 20fps
```

这条已固化进 `display` 模块的骨架接口（`acquireBack()` / `present()` + core 0 刷屏任务）。

**库选型**：用 JPEGDEC（不换 esp_new_jpeg）。虽然 esp_new_jpeg 快 16～17%，
但 Arduino 封装库 `ESP32_JPEG` 已停更三年（封装的是旧版），要用官方 IDF 组件才有加速，门槛高。
若真机实测帧率不够再迁移，`decoder` 已做成可替换接口。

320×180 站得住，不退 240×135。详见 [阶段0-实测报告.md](阶段0-实测报告.md)。

### 阶段 1 · 点亮与播通一段（2～3 天）— **先放 Flash，不碰 SD 卡**

> 决策调整：原计划一上来就挂 SD 卡。改为**第一阶段先把动画烧进 Flash**，
> 排除卡挂载、卡质量、接触不良等干扰，专注跑通「取帧 → 解码 → 刷屏 → 循环」。
> 跑通后阶段 2 再加 SD 卡——两个阶段共用同一份 `.petpack` 与同一套读取代码，
> 差别只在 `storage` 返回哪个 `fs::FS&`。

Flash 比 SD 更适合跑通：读 6KB < 1ms（SD 约 5ms）；JPEGDEC 支持从 Flash **内存直解**，
可省一次 6KB 拷贝和一块 RAM。

分区表（去掉 OTA，一步到位预留 11.9MB）：

```
nvs,      data, nvs,     0x9000,    0x5000,
otadata,  data, ota,     0xe000,    0x2000,
app0,     app,  ota_0,   0x10000,   0x400000,    ; 4MB 固件
storage,  data, spiffs,  0x410000,  0xBF0000,    ; 11.93MB 动画（LittleFS）
```

容量账（实测每段平均 0.73MB）：完整 10 秒版约 **16 段**；3 秒精简版约 56 段。
**第一阶段只烧 5 段**（待机 + 拖拽 + 点击×2 + 工作状态，约 3.5MB），跑通后再补满。

> ⚠️ 文件系统必须用 **LittleFS 而非 SPIFFS**：SPIFFS 不支持真目录（扁平结构），
> 而我们的 pack 是按分类分目录放的。

## 六、风险与备选方案

| 风险 | 概率 | 应对 |
|:---|:--:|:---|
| JPEG 解码跟不上 12fps | 中 | 降到 240×135；或改 **RGB565 + RLE**（解码 1～2ms，帧体积 20～40KB，SD 带宽 1MB/s 也扛得住） |
| SD 卡随机读太慢 | 低 | 容器内保证顺序读；SD 走 4-bit SDMMC 而非 SPI；实在不行降到 160×90 |
| 屏幕刷不平（撕裂） | 中 | 双缓冲 + DMA；屏开 TE 引脚或把 SPI 拉到 80MHz |
| 51MB 素材放不下 Flash 想省卡 | 中 | 只保留 20 段核心动画（约 20MB），用 32MB 的 S3 模组（N32R8）直接塞 Flash |
| 透明边缘发黑 | 高（若用色键） | 优先预合成背景；非要抠像就把色键容差调大 + 边缘羽化 1px |

## 七、一句话版本

> **把 106 段 webm 转成 320×180 / 12fps / q75 的 JPEG 帧，打包成带偏移表的 `.petpack`，扔进 SD 卡；ESP32-S3（16M Flash + 8M PSRAM）+ 320×240 SPI 屏 + LovyanGFX + JPEGDEC，双缓冲 DMA 刷屏，12fps 稳跑，先用 3 天做通一段，再用 1 周做成产品。**

如果要更省事、体积更小、帧率更高，唯一的替代路线是 **RGB565 + RLE 自研帧格式**（解码几乎零成本，但要自己写编码器 + 透明掩码），适合做到第二阶段后觉得 MJPEG 不够再换。
