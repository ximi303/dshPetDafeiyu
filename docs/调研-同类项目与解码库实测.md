# 调研：同类开源项目 & JPEG 解码库实测

> 调研时间：2026-10-27
> 目的：① 确认有没有可以直接抄的同类项目；② 用真实实测校准原方案里拍脑袋的性能预算。

---

## 一、同类项目：桌宠很多，但对标的没有

| 项目 | 硬件 | 动画怎么来的 | 与我们的差距 |
|:---|:---|:---|:---|
| **ESPets**（kuspys） | ESP32-S3 + 240×240 IPS | LVGL 像素画 + PlatformIO | 目录就是 `firmware/ hardware/ docs/ assets/` —— **与我们的四分区几乎一致**；但动画是画的，不是播的 |
| **DogePet**（TinkerDoge） | ESP32-S3 SuperMini + 128×64 OLED | FluxGarage_RoboEyes 程序绘制眼睛 | 代码画眼睛，Arduino IDE，无素材管线 |
| Claude Buddy | ESP32 | 18 种 ASCII 动物字符动画 | 字符级，非视频 |
| QBIT | ESP32-C3 + OLED | OLED 表情 + MQTT | IoT 传呼定位 |
| Sentio | ESP32-S3-Box-3 | 语音陪伴机器人 | 重点在语音 |
| FUMI | ESP32-S3 | AI 陪伴（含饥饿值/亲密度） | 商业项目，闭源部分 |
| Moji 2.0 / 小智 | ESP32-C5 / C3 | AI 语音助手 + 表情 | 重点在 LLM 对话 |
| DeskBuddy | OLED | 表情动画 | 低分辨率 |
| ESP32VirtualPet | 墨水屏 1.54" | 电子宠物养成 | 墨水屏刷新率不够 |
| **ESP32 MJPEG TV**（open-electronics） | ESP32 + 2.4" TFT | **真的从 SD 卡播 MJPEG 视频** | 播放链路和我们一样，**但只是播放器，没有桌宠状态机、没有素材管线** |
| ASCII 水族箱 | ESP32 + 320×240 | ASCII 实时渲染 | 完全不同的路子 |

### 结论

1. **没有对标项目。** 现有桌宠全是「用代码画一只宠物」（LVGL 像素画 / RoboEyes / ASCII），
   没有一个是「把现成的上百段真实动画素材搬到 ESP32 上播放 + 带状态机」。
2. 因此这三样**必须自研**，抄不到：
   - **`.petpack` 容器**（22 字节头 + 偏移表 + 连续 JPEG）
   - **alpha 预合成**（把透明区烘焙进背景色，固件不做逐像素 alpha）
   - **权重抽签状态机**（从 `assets/animations.json` 移植 dsh-pet 的动画池逻辑）
3. 能直接复用的：ESPets 的目录组织（反向验证四分区方向正确）、MJPEG 播放链路、
   JPEGDEC 的 ESP32-S3 SIMD 支持。

## 二、JPEG 解码库实测：修正了原方案的性能估算

### 2.1 一个好用的巧合

**320×180 = 57,600 像素，240×240 也 = 57,600 像素。**
所以别人的 240×240 实测数据，可以直接当成我们 320×180 的数据用。

### 2.2 主数据源（ESP32-S3-Zero @240MHz，Lenna q80，Arduino 生态，10 次平均）

| 分辨率 | 库 | Decode(ms) | Draw(ms) | 合计(ms) | FPS |
|:---|:---|--:|--:|--:|--:|
| **240×240（= 我们的 320×180）** | **JPEGDEC** | **28.91** | **28.10** | **57.01** | 17.5 |
| | ESP_NEW_JPEG（乐鑫官方最新） | 17.44 | 30.48 | 47.92 | 20.9 |
| | Tjpg_Decoder | 43.85 | 51.13 | 94.98 | 10.5 |
| 320×240 | JPEGDEC | 38.12 | 38.21 | 76.33 | 13.1 |
| | ESP_NEW_JPEG | 23.99 | 39.60 | 63.59 | 15.7 |
| | Tjpg_Decoder | 57.63 | 68.10 | 125.73 | 8.0 |
| 160×80 | JPEGDEC | 7.42 | 6.91 | 14.33 | 69.8 |
| | ESP_NEW_JPEG | 3.75 | 6.17 | 9.93 | 100.8 |

### 2.3 交叉验证（ESP32S3@240MHz + ILI9341 240×240 + SPI 60Mbps）

| 方案 | 解码一帧 240 方图 |
|:---|--:|
| IDF 自带 tiny jpeg | 48 ms |
| JPEGDEC 纯 C | 22 ms |
| **JPEGDEC 开 SIMD** | **13 ms** |
| esp_new_jpeg | 7 ms |
| **GIF（gifdec）** | **80～350 ms，且 RAM 需 7×像素数（约 400KB）→ 不可用** |

刷屏：240×240 **开 DMA 22～23 ms**，关 DMA 41～42 ms；SPI 60Mbps 理论 15.36ms → **实际效率约 60%**。

### 2.4 对原方案的修正

原 `ESP32桌宠技术方案.md` 4.4 节估算「解码 15～25ms + 刷屏 15ms ≈ 45ms，余量 40%」。

| 项 | 原估算 | 实测 | 偏差 |
|:---|--:|--:|:---|
| JPEG 解码 | 15～25 ms | **28.91 ms** | 偏乐观 |
| 刷屏 | 14～18 ms | **28.10 ms** | 偏乐观 |
| 合计 | 35～53 ms | **57.01 ms** | — |
| 12fps(83ms) 余量 | 40% | **31%** | 需修正 |

**结论：方案不用推翻，12fps 依然站得住，但余量是 31% 不是 40%。**

### 2.5 由此得到的最大优化点：双核并行

上面 57ms 是 **decode 与 draw 串行相加**的结果。ESP32-S3 是双核，
让「核 1 解下一帧」与「核 0 DMA 刷当前帧」通过双缓冲重叠，帧时间就从

```
sum(decode, draw) = 57ms
        ↓
max(decode, draw) ≈ 29ms
```

→ 12fps 余量从 31% 提到 64%，理论可冲 20fps。**这条已写进 `display` 模块的骨架接口。**

### 2.6 库选型决策

**选 JPEGDEC**，不换 esp_new_jpeg。理由：

- PlatformIO 一行引入，生态成熟，开箱自带 ESP32-S3 SIMD 汇编（`s3_simd_420.S` / `s3_simd_444.S` / `s3_simd_dequant.S` / `s3_simd_idct.S`）
- 官方支持「JPEG data from memory (FLASH/RAM) / SDCard / 任意介质」——
  **阶段 1 放 Flash 时能直接从 Flash 内存解码**，省一次 6KB 拷贝和一块 RAM，这是 SD 阶段拿不到的优势
- esp_new_jpeg 虽快 16～17%，但 Arduino 封装库 `ESP32_JPEG` 已停更三年（封装的是旧版），
  要用官方 `esp-adf-libs/esp_new_jpeg` 才有加速，属于 IDF 组件，配置门槛高

**备选**：若真机实测帧率不够，再考虑迁移到 esp_new_jpeg。`decoder` 模块已做成可替换接口。

## 三、其他踩坑经验（来自上述实测文章）

1. **刷屏要用 DMA**：同样 240×240，开 DMA 22ms / 关 DMA 42ms，差一倍。
2. **SPI 是最终瓶颈**：有博主实测到「撞上 SPI 上限」。320×180×2B = 113KB，
   SPI 80MHz 理论 ~11ms，实际 ~28ms。想再快只能换 8bit 并口屏或 QSPI 屏。
3. **GIF 彻底排除**：解码 80～350ms 且 RAM 需 7×像素数，ESP32-S3 跑不动。印证 MJPEG 选型。
4. **屏幕调试三件套**：黑屏查背光；XY 反了/镜像查 `MADCTL(0x36)`；偏色查大小端与 RGB/BGR。
